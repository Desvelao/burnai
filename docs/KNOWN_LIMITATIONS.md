# Known limitations

- **Automatic usage uses an unofficial endpoint.** `claude.ai/api/oauth/usage` is undocumented and can change, rate-limit, or answer 403 (Cloudflare bot challenge) at any time; the browser-like User-Agent is a workaround you can edit per account. The access token is read from the credentials file and is never refreshed: when it expires, run `claude` to log in again (the app will show this). Not verified against the live endpoint during development (tests use a local stub). When it fails, usage goes stale and execution is blocked; enter usage manually as a fallback.
- **Billing verification is conservative, not a proof.** It checks env vars, the existence of a local login file in the account's profile dir (default `~/.claude`) and your explicit confirmation. Credential file locations vary by platform/CLI version; if the check does not recognise your login the account stays `Unverified` and blocked. Verify against your Claude Code version before relying on it.
- **Real `claude` CLI only partly exercised.** On 2026-11-04 (Claude Code 2.1.318) one manual `echo "Reply with exactly: ok" | claude -p --output-format text --model haiku` run exited 0 and printed `ok` on stdout; the CLI also wrote a sign-in-expiry warning to stderr, which the runner keeps separate from stdout. `~/.claude/.credentials.json` exists at the path billing detection checks. Not verified: the full runner/preflight against the real CLI, the real rate-limit message (the markers in `claude.rs` are guesses and only consulted on a non-zero exit; `429`/`quota` may match unrelated failures), and billing detection against API-key setups.
- **GUI not launched in the development environment.** It compiles and lints in Docker; display forwarding (`make gui`) requires you to grant X access, and was not run here. Treat GUI behaviour as untested until you run it.
- **Idle detection** requires `xprintidle` (X11). Otherwise idle is "unknown" and an idle requirement is never met.
- **Descendant processes** that leave the child's process group are not terminated by STOP/timeouts.
- **Email notifications** are not implemented. Desktop notifications need a notification daemon; Telegram is notify-only.
- **Drag-and-drop reordering** (GUI queue: drag the ☰ handle onto another row; ▲/▼ remain) compiles, lints and its core logic (`tasks::move_next_to`) is unit-tested, but the drag interaction itself was not run in a GUI session. With a filter active, the move is applied relative to the full queue order. The TUI uses keys only.
- **Linux only** so far (Unix process-group handling).
- Actual consumption is never measured automatically; it is entered by the user. Until then the estimate is used for accounting and labelled as an estimate.
- **Custom provider scripts are trusted code.** They run with your privileges; the app cannot verify what they bill or whether their `usage` numbers are true (shown as script-reported). Descendants a script leaves outside its process group survive STOP/timeouts. The example script is a skeleton, not an integration. Only unit-tested with local test scripts.
- **Host binary** (`make dist`) is built against Debian bookworm (glibc >= 2.35 for the GUI, 2.34 for the TUI/tray; the build image is pinned in `Dockerfile.dev`), Linux x86_64 only, unstripped, with no installer; it renders a systemd user unit and `.desktop` file into `dist/` but installs nothing. Not executed on the host by me.
- **TUI** (`make tui`) has the same features as the GUI (see `docs/FEATURE_PARITY.md` for the matrix and the few interaction differences, e.g. JSON+CSV history export is one key and drag-reordering is GUI-only). Covered by `TestBackend` render and key-driven tests in the container; no interactive terminal session was run, and the OSC 52 copy works only in terminals that support it.
- **`daily:HH:MM` task schedule is not a recurrence:** it only means "not before that local time of day". To repeat a task use its separate *Repeat* rule (`every:6h`, `daily:09:00`, `weekly:mon-fri@18:30`): when a run ends (completed, failed or expired, not cancelled) one new Pending copy is queued with `schedule = after:<next time>`. At most one live copy per name+rule exists; a manual Retry of a failed run can therefore coexist with its successor. The copy drops any expiry, and repeating is measured from when the previous run finished, not from a fixed grid.
- **Billing guard scope:** besides env vars, `safety` scans Claude Code settings (`<config dir>/settings.json`, `/etc/claude-code/managed-settings.json`, and `.claude/settings{,.local}.json` from the task directory up to its git root) for `apiKeyHelper`, `forceLoginMethod=console`, cloud auth hooks and billing `env` entries (⇒ API, task blocked); unreadable/invalid files ⇒ unverified. The child env is a denylist (not an allowlist), so unknown future billing variables are not scrubbed, and settings in locations Claude Code might read that we do not (e.g. CLI flags in a wrapper `cli_command`) are not inspected.
- **Clients need the scheduler daemon for every change:** settings, account and task writes and all actions are forwarded to it; with no daemon they are refused with "the scheduler is not running" and the client offers Start scheduler.
- **Hung daemon:** if the socket accepts connections but does not answer, clients show "scheduler not responding" and can only read; restart the daemon yourself (Start scheduler is offered only when it is offline). Flock and the socket are unix-only. Approvals are in the driver's memory, so they are lost if it restarts.
- **Tray** (`plan-burner-tray`): needs a StatusNotifierItem host (KDE, most bars/Waybar; GNOME needs the AppIndicator extension). Logic (IPC, launch helpers, forwarding) is unit-tested in the container; the icon and menu themselves were not exercised on a desktop. Autostart is up to you (`make dist` renders a systemd user unit and a `.desktop` file, nothing is installed).
- **Icons:** drawn and unit-tested in the container and inspected as exported PNGs (all states, 16 px included). The live tray icon relies on the SNI host honouring `IconPixmap` (KDE and Waybar do; a host that only reads themed names will show nothing), and the runtime window-icon update was not seen on a real desktop. The `.desktop` file references `Icon=<slug>`: copy `dist/<slug>.png` to `~/.local/share/icons/hicolor/256x256/apps/`.
- **Changing `brand.toml`'s `slug` or `db_file`** points the app at a new data directory/database; existing data is not migrated.

- **Browse… needs an xdg-desktop-portal.** Without one (or in the dev container without the session bus), the dialog does nothing and the path must be typed. In the container, picked host paths outside the mounted volumes will not exist.
- **Installer:** `install.sh` is tested in the container against a tarball packed from `make dist` (`make install-test`, with `--no-systemd`). It has not been run against a real GitHub release, with a real `systemctl --user` session, or on non-Debian distributions. It needs `curl` or `wget`, `tar`, `awk` and `sha256sum`/`shasum`.
